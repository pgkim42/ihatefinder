## 판정: BLOCK — 방향은 맞지만 아직 ‘불만의 원인에 대한 판단’보다 기능 묶음에 가깝다

제안은 기능 부재를 과장하지 않고 조건부 순서를 둔 점은 좋다. 그러나 아래 네 blocker를 고치지 않으면 사용자는 “그래서 내 앱에서 다음에 딱 무엇을 해야 하나”보다 또 하나의 기능 체크리스트를 받게 된다.

### B1 — CG11: 첫 increment가 서로 다른 가설 세 개를 한 번에 묶는다

`내 장소 + 주소 후보 + 기존 명령 노출`은 하나의 increment가 아니다.

- **내 장소**는 다시 갈 위치를 사용자가 명시적으로 저장하는 기능이다(CG02). 반복 목적지가 분명할 때 유효하다.
- **최근 장소**는 사용자가 저장하지 않은 방문 이력을 재사용하는 기능이다(CG03의 주소 후보와도 별개). 아직 제안 문구에서 즐겨찾기와 구분되지 않는다.
- **주소 후보**는 목적지의 일부를 기억하지만 전체 경로는 모를 때 입력을 완성하는 기능이다(CG03).
- **명령 노출**은 장소 탐색이 아니라 이미 구현된 F5/F6·Quick Look을 발견하게 하는 작은 표면 수정이다(CG06).

이 셋을 함께 만들면 무엇이 불만을 줄였는지 알 수 없고, 탭을 제외해 범위를 줄였다는 장점도 희석된다. **기본 첫 increment는 ‘기존 명령 노출’ 하나로 좁히는 것이 가장 구체적이다.** `반대쪽 [현재 폴더명]으로 복사 (F5)`, `…이동 (F6)`, `Quick Look (Space)`를 메뉴 또는 문맥 메뉴에 같은 실제 action으로 연결하고, 거르기 메뉴를 실제 범위에 맞게 이름 붙이는 수준이다. 새 상태 모델이 없고 현재 제품의 양쪽 창 가치를 바로 설명한다. 이것은 효과 측정이 아니라 코드 범위와 제품 의도에 따른 판단이다.

그 다음 increment는 작업에 따라 **내 장소 또는 주소 후보 중 하나**를 고른다. 둘을 자동으로 한 묶음으로 만들지 않는다.

### B2 — CG02·CG03·CG05: 즐겨찾기, 최근 장소, 탭을 ‘장소 접근’으로 합치면 안 된다

세 기능은 해결하는 불만이 다르다.

1. **즐겨찾기/내 장소**: 자주 가는 고정 프로젝트를 다시 찾는 비용을 줄인다. 현재 기본 장소와 디스크는 있지만 사용자 등록·삭제·정렬·영속 모델은 없다(CG02). Finder 공식 문서도 Favorites에 폴더를 추가·재배열하는 기능을 별도로 둔다.
2. **최근 장소**: 방금 또는 지난 세션에 갔던 임시 위치를 사용자가 미리 등록하지 않고 되찾는다. 현재 back/forward와 마지막 좌우 위치 복원은 있으나 재사용 가능한 최근 목록은 없다. Finder 공식 `Recent Folders`와 Marta의 tab-local recent가 이 구분을 보여 준다.
3. **탭/추가 작업 자리**: A/B의 선택·방문 맥락을 유지한 채 C를 별도로 연다(CG05). 즐겨찾기는 C에 빨리 가게 할 뿐 A/B/C를 동시에 보존하지 않는다. QSpace workspace와 Nimble Commander tabs가 공식적으로 이 작업을 맡는다.

따라서 “추가 독립 작업 자리와 선택/스크롤 유지”도 하나의 항목으로 묶지 말아야 한다. 추가 자리 생성은 세션 수명·전송 대상·복원 모델을 넓히는 기능이고, 선택/스크롤 복원은 기존 두 자리의 왕복 품질이다. 후자가 더 작은 increment다.

### B3 — CG04: 현재 폴더 거르기와 현재 폴더 밖 찾기를 기능 단계로 명확히 분리해야 한다

현재 Cmd-F는 이미 읽은 현재 폴더의 이름 목록만 줄이며 실제 GUI에서도 README 두 행으로 동작했다(CG01·CG04, `verify-desktop.md` GUI3). 이것을 “검색”이라고 부르면 구현된 것을 누락으로 오진하고 사용자의 기대도 잘못 설정한다.

별도 찾기를 권한다면 완료 기준을 붙여야 한다: **검색 범위 표시, 원래 경로 표시, 취소, 읽지 못한 폴더 처리, 결과에서 부모 폴더 열기/항목 선택, 기존 복사·이동으로 연결**. Nimble Commander 공식 문서의 검색 결과 temporary panel과 QSpace의 pane search/Spotlight 분리는 ‘결과를 발견하는 것’보다 ‘결과를 기존 작업으로 넘기는 것’이 중요하다는 근거다. Spotlight 연동, 자체 재귀 이름 검색, Finder식 메타데이터 검색은 서로 다른 선택이며 한 번에 요구하지 않는다.

### B4 — CG01·CG07: 안전 엔진과 복구 UX의 차이를 더 앞에서 밝혀야 한다

현재 앱에는 진행·취소·부분 결과·경로·복구 위치·보수적 undo가 있다(CG01). 그러므로 “안전성이 부족하다”는 진단은 틀리다. 확인된 부족은 **결과 시트를 닫은 뒤 다시 열기, 보존 위치로 이동·선택하기, 실패·미처리만 다음 행동으로 연결하기가 어렵다**는 것이다(CG07).

다만 이것을 모든 사용자에게 장소 접근보다 우선한다고 단정할 근거도 없다. 실패·부분 완료를 실제로 겪는 작업에서는 최우선이고, 주로 작은 로컬 복사만 성공시키는 흐름에서는 후순위다. 첫 구현도 전송 엔진 재작성이나 거대한 queue가 아니라 `최근 작업 1건 재열기 + 위치 열기/선택 + 상태별 다음 행동`으로 제한해야 한다. 확인된 mount notification-center mismatch(CG12)는 이 축의 작은 실제 결함으로 별도 수정 후보이며, 물리 디스크 실패가 관측됐다고 확대하면 안 된다.

## 조건부 권고 순위

아래는 사용자 빈도 측정이 아니라 **현재 구현과 서로 반대되는 작업 시나리오에 따른 제품 판단**이다. 일기를 요구하지 않아도 사용자가 자신의 주된 이탈 장면에 가장 가까운 분기를 고를 수 있다.

1. **공통 선행 — 기존 강점을 보이게 한다.** F5/F6·Quick Look의 명시적 메뉴/문맥 메뉴 진입점과 대상 폴더 표시, ‘찾기’를 ‘이 폴더에서 이름 거르기’로 정밀화한다(CG06). 가장 작고 현재 제품 정체성에 직접 연결된다.
2. **정확히 아는 몇 개 프로젝트를 반복 방문한다면 — 내 장소부터.** 사용자 폴더 추가·삭제·재배열·영속화만 첫 범위로 한다(CG02). 최근 장소와 주소 후보는 별도 후속이다.
3. **경로 일부는 기억하지만 전체 경로를 자주 못 외운다면 — 주소 후보부터.** 현재 `~`·직접 경로 입력은 유지하고, 폴더 후보·Tab 수락·키보드 선택을 붙인다(CG03). Apple의 공식 Go to Folder도 suggested pathnames와 recent pathnames를 구분한다.
4. **파일 이름은 알지만 어느 하위 폴더인지 모른다면 — 재귀 이름 찾기부터.** 현재 거르기는 그대로 두고 별도 결과 모델을 만든다(CG04). 이 경우 즐겨찾기·주소 후보·탭은 문제를 해결하지 않는다.
5. **A/B를 유지한 채 C의 선택·방문 상태까지 자주 보존해야 한다면 — 추가 자리 하나.** 새 창 또는 pane별 탭 중 하나만 고른다(CG05). 둘과 named workspace를 동시에 만들지 않는다. 단순히 C로 빨리 이동하는 문제라면 즐겨찾기가 더 작다.
6. **부분 실패 뒤 Finder나 터미널에서 복구 위치를 다시 찾는다면 — 결과→다음 행동 흐름.** 최근 결과 재열기, 살아 있는 위치 열기/선택, 실패·미처리·경고 분리부터 한다(CG07). 안전 엔진 전체를 다시 만들지 않는다.
7. **사진/PDF를 내용으로 고르는 일이 중심이면 — 상시 미리보기/thumbnail을 위로 올린다.** Quick Look은 이미 있으므로 Finder의 네 view 전체가 아니라 판별 단계를 줄이는 최소 표면만 검토한다. 이 작업이 아니라면 후순위다.

## ‘0.3 Finder’ 해석

`0.3`은 30% 기능 점수도, Finder 기능 10개 중 3개를 채우라는 뜻도 아니다. 정량 근거가 전혀 없으므로 백분율·점수표를 만들면 안 된다. 여기서는 **주소 입력·상세 목록·잘라 옮기기·양쪽 창이라는 목표 작업 중, 사용자가 Finder로 되돌아가지 않고 한 흐름을 끝낼 수 있는 최소 실용성**으로 해석하는 것이 맞다. 따라서 기능 개수보다 “어디서 흐름이 끊기며, 다음 행동까지 이어지는가”로 판단해야 한다.

## 불필요하거나 지금 강제하면 안 되는 것

- Finder를 모든 시스템 표면에서 제거하기. Marta도 Get Info/Reveal에 Finder를 쓰고 ForkLift도 시스템 Open/Save 대체를 약속하지 않는다(CG09).
- 탭·다중 창·named workspace를 동시에 구현하기.
- 즐겨찾기·최근 장소·주소 후보를 하나의 ‘navigation’ epic으로 한 번에 구현하기.
- Spotlight·자체 재귀·내용/태그/날짜 검색·Smart Folder를 한 검색 기능으로 묶기.
- 원격 프로토콜, 양방향 sync, embedded terminal, transfer queue를 최소 실용성의 필수조건으로 두기. 현재 외부 Terminal, 진행·취소, 안전한 단일 작업 기반이 이미 있다.
- Finder의 icon/list/column/gallery 네 view를 모두 복제하기. 상세 목록은 제품 의도이며 Quick Look도 구현돼 있다.
- 사용자 diary가 없다는 이유로 결정을 미루기. 위 분기형 권고는 인과 측정이 아니라 명시된 작업별 판단이며, 사용자는 자신이 Finder로 돌아가는 대표 장면 하나만 대입하면 된다.

## 최종 답변에 쓸 수 있는 한 문장 판단

**지금 IHateFinder에 가장 아쉬운 것은 기능 수가 아니라, 이미 잘하는 ‘두 폴더 사이의 상세 목록 작업’을 사용자가 발견하고 끝까지 이어 가게 하는 연결이다. 먼저 F5/F6·Quick Look·거르기의 표면을 정리하고, 그다음 Finder로 돌아가는 장면이 반복 장소인지, 위치 미상 파일인지, 세 번째 작업 맥락인지, 부분 실패 복구인지에 따라 내 장소·검색·추가 자리·결과 복구 중 하나만 다음 increment로 고르는 편이 ‘0.3 Finder’에 가장 빨리 도달한다.**

## EXPAND

- 새 코드 조사 blocker는 없음. CG01–CG12와 공식 Apple/Marta/QSpace/ForkLift/Nimble 문서만으로 위 구분이 닫힌다.
- 남은 것은 사용자 빈도에 대한 **unknown**이지 제안의 모순이 아니다. 위 순위를 보편적 빈도 주장으로 쓰지 않고 조건 분기로 제시하면 diary 없이도 실행 가능한 판단이 된다.
- CG12의 notification-center 계약 불일치는 확인됐지만 물리 mount incident는 **unknown**이다. 좁은 코드 결함으로만 언급하고 제품 불만의 주원인으로 승격하지 않는다.
- 대량 성능, 특수 볼륨, cloud/provider E2E, native Quick Look 내부 공유는 **unknown**이다. 현재 제안과 충돌하지 않으며 최소 첫 increment의 근거로 사용하지 않는다.
