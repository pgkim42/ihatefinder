## Skeptic 축 결론

초기 가설인 “검색·즐겨찾기/장소 전환·통합·신뢰감이 핵심 결핍이다”는 현재 증거만으로는 우선순위 결론으로 성립하지 않는다. 이 다섯 항목 중 **검색은 ‘현재 폴더 거르기’와 ‘하위 폴더/Spotlight 검색’을 분리해야 하고**, **장소 전환·통합·신뢰 안전장치는 이미 상당 부분 구현돼 있으며**, **사용자 정의 즐겨찾기만 명확히 부재**한다. 그러나 그 부재가 실제 사용 중 Finder로 돌아가는 가장 잦은 원인이라는 빈도 증거는 저장소·브리프 어디에도 없다. 따라서 최종 보고서는 이 기능 묶음을 “핵심”이라고 선결론 내리지 말고, 관찰된 이탈 작업의 빈도와 비용으로 검증할 가설로 낮춰야 한다.

관찰 시점/유효 범위: 2026-10-10, 현재 브랜치 HEAD `0970c61`. 코드·README·`docs/behavior.md`를 직접 읽은 정적 관찰이다. 앱 런타임 실패나 실제 사용자 빈도는 관찰하지 않았고 단언하지 않는다. 제품 코드·문서·설정·git 기록을 수정하지 않았다. `git status --short`에서 `doc/`가 이미 untracked로 보였으며 손대지 않았다.

## 주장별 공격

### 1. “검색이 핵심 결핍” — 용어 혼동과 빈도 미확인

**관찰 O1 (구현됨, 독립 그룹: 동작 문서):** `docs/behavior.md:48-52`는 Cmd/Ctrl-F와 F3로 현재 폴더의 이름을 즉시 거르고, 대소문자·악센트를 구분하지 않으며, 선택·상태 표시·외부 갱신과 함께 동작한다고 명시한다. `README.md:119-129`도 같은 사용자 표면을 설명하면서 “현재 폴더만, 하위 폴더는 아님”을 명시한다.

**관찰 O2 (구현됨, 독립 그룹: 코드):** `Sources/IHateFinder/FilePaneController.swift:122-129`는 실제 `NSSearchField`와 즉시 전송 action을 구성하고, `Sources/IHateFinder/FilePaneController.swift:287-337`는 표시·초점·Esc 처리·필터 적용·선택 보존을 구현한다. `Sources/IHateFinderCore/EntryFilter.swift:3-10`은 trim 후 `localizedStandardContains`로 이름을 거른다. 이는 문서의 희망사항만이 아니라 생산 코드 경로다.

**관찰 O3 (명확한 한계):** `README.md:229-236`와 `docs/behavior.md:149-153`은 하위 폴더 검색이 이번 버전에 없다고 명시한다. `CONTEXT.md:63-65`는 이 기능을 의도적으로 “검색”이 아닌 “거르기”로 정의한다.

**반박:** “검색 없음”은 거짓이고, “재귀/Spotlight 검색 없음”은 참이다. 그러나 후자가 일상 대체성의 핵심이라는 증거는 없다. 정확한 질문은 “사용자가 이미 폴더를 알고 그 안에서 이름을 좁히는가, 위치를 모른 채 전역으로 찾는가”이다. 전자라면 현재 구현이 요구를 충족한다. 후자 빈도가 높을 때만 재귀/Spotlight가 핵심이 된다.

**반증 가능 조건:** 실제 작업 일지에서 ‘위치를 몰라 Finder/Spotlight로 검색’이 상위 이탈 사유이고, 현재 폴더 거르기로 해결되지 않는 사례가 반복될 때 검색 우선 주장이 강해진다.

### 2. “즐겨찾기/장소 전환이 핵심 결핍” — 절반만 참

**관찰 O4 (장소 전환 구현됨, 독립 그룹: 동작 문서):** `docs/behavior.md:8-14`는 뒤/앞/위 이동과 홈·데스크탑·문서·다운로드·응용 프로그램 및 디스크 사이드바를 정의한다. `docs/behavior.md:16-18`은 직접 경로 입력도 정의한다.

**관찰 O5 (장소 전환 구현됨, 독립 그룹: 코드):** `Sources/IHateFinder/BrowserWindowController.swift:528-632`는 실제 source-list 사이드바와 뒤/앞/위 버튼을 구성한다. `Sources/IHateFinder/BrowserWindowController.swift:848-878`은 다섯 고정 위치와 탐색 가능한 마운트 볼륨을 생성한다. `Sources/IHateFinderCore/BrowserSession.swift:79-111`은 직접 이동과 뒤/앞/위 이력을 구현한다.

**관찰 O6 (사용자 정의 즐겨찾기 부재):** `Sources/IHateFinder/BrowserWindowController.swift:848-878`의 장소 집합은 고정 위치와 현재 볼륨으로만 구성되고, `Sources/IHateFinderCore/WorkspaceStore.swift:3-48`의 저장 스키마에는 좌우 경로·정렬·숨김·양쪽 창 상태만 있다. 저장된 사용자 장소/북마크 필드가 없다. `favorite|favourite|bookmark|즐겨찾기|사용자 장소|custom place|saved place|pinned` 변형 검색에서도 구현 항목이 없고, `CONTEXT.md:30-33`은 사이드바를 “자주 가는 위치와 디스크”라고 부를 뿐 사용자 편집성을 약속하지 않는다.

**반박:** “장소 전환 없음”은 틀리다. 정확한 부재는 “사용자가 임의 폴더를 고정하는 즐겨찾기”이다. 더구나 마지막 좌우 폴더가 복원되므로(`README.md:158-168`, `Sources/IHateFinderCore/WorkspaceStore.swift:70-93`) 반복 작업의 일부는 이미 줄어든다. 사용자 정의 즐겨찾기를 구현해도 사용자가 대부분 홈/다운로드/프로젝트 한두 곳만 쓰거나 주소창으로 경로를 붙여넣는다면 효과가 작을 수 있다.

**반증 가능 조건:** 실제 이탈 사례가 “고정 사이드바와 복원으로 닿지 않는 여러 작업 루트에 반복 이동”으로 모이고, 주소창/뒤로/복원보다 사용자 핀이 유의하게 단축할 때 즐겨찾기 우선 주장이 강해진다.

### 3. “통합이 핵심 결핍” — 범위를 뭉뚱그리면 이미 구현된 통합을 지운다

**관찰 O7 (클립보드·드래그 통합 구현됨, 독립 그룹: 문서):** `README.md:61-79`는 Finder와 시스템 클립보드를 공유하고 Finder/IHateFinder 사이 복사를 지원하며 드래그의 이동/복사 규칙을 설명한다. `docs/behavior.md:54-68`은 외부 파일 URL 클립보드와 세대 안전성을, `docs/behavior.md:123-124`는 Finder에서 끌어온 항목 처리를 명시한다.

**관찰 O8 (외부 열기/reveal 통합 구현됨, 독립 그룹: 코드):** `Sources/IHateFinder/AppDelegate.swift:8-37`은 cold launch 전에 `Show in Finder` Apple Event와 open-documents URL을 수신하고 실제 라우터로 전달한다. `Sources/IHateFinder/BrowserWindowController.swift:199-218`은 최소화 해제·활성화 후 폴더 이동 또는 부모 이동+선택으로 소비한다. 생산자만 있고 소비자가 누락된 형태가 아니다.

**관찰 O9 (기본 파일 뷰어 절차와 한계가 명시됨):** `README.md:171-227`은 사용자가 직접 `NSFileViewer`/LaunchServices를 설정하는 절차와 함께 Open/Save 패널, Desktop, Dock Finder 아이콘, Finder 직접 호출 앱은 계속 Finder를 쓴다고 명시한다. `docs/behavior.md:139-147`도 같은 경계를 기록한다.

**반박:** “macOS 통합 부족”은 너무 넓어 행동 가능한 주장이 아니다. 이미 구현된 통합(클립보드, Finder 드래그, open/reveal 요청, 기본 파일 뷰어 설정)과 구조적으로 Finder가 남는 표면(Open/Save, Desktop, Dock, 직접 호출)을 분리해야 한다. 후자는 앱 내부의 작은 기능 한두 개로 모두 제거할 수 있는 결핍이 아니다. Finder 재등장이 곧 IHateFinder 통합 실패라는 인과도 성립하지 않는다.

**반증 가능 조건:** 실제 빈번한 외부 앱이 IHateFinder로 전달 가능한 요청인데도 전달되지 않거나, 지원된 clipboard/drag/open 경로가 관찰상 실패할 때 구체적 통합 결함으로 승격할 수 있다. 현재 조사는 그러한 런타임 실패를 관찰하지 않았다.

### 4. “신뢰감이 핵심 결핍” — 안전성과 체감 신뢰를 혼동

**관찰 O10 (안전장치 구현·문서화, 독립 그룹: 사용자 문서):** `README.md:61-70`은 충돌 시 Replace/Skip/Keep both를, `README.md:95-117`은 Trash-only 삭제와 안전한 undo 조건을, `README.md:140-156`은 취소·부분 완료·복구 위치·APFS clone을 설명한다.

**관찰 O11 (세부 안전 계약, 독립 그룹: 동작 문서):** `docs/behavior.md:70-90`은 대체 전 staging, 실패 시 복구, 원본/기존 대상 보존을 규정한다. `docs/behavior.md:92-106`은 진행·취소·부분 결과를, `docs/behavior.md:116-121`은 50개 undo journal과 stale/occupied/unverifiable 조건에서 건너뛰는 정책을 명시한다.

**관찰 O12 (실제 코드 상태):** `Sources/IHateFinder/BrowserWindowController.swift:23-29`에 busy 상태, undo journal, 결과 보고가 있고, `Sources/IHateFinderCore/FileUndo.swift:43-68`은 created/copied/moved/renamed/trashed 역연산과 실패 상태를 모델링한다. `Sources/IHateFinderCore/FileOps.swift:79-91`은 교체·휴지통·대상 identity·same-volume 이동 결과를 경계 밖으로 전달한다.

**반박:** “신뢰감”은 관찰 변수가 아니라 해석이다. 현재 증거로는 안전 메커니즘 부재를 주장할 수 없고 오히려 이 앱은 안전한 파일 작업을 강하게 우선한다. 사용자가 불신한다면 원인은 실제 오류율, 상태 표시의 가시성, 생소한 UI, Finder 브랜드 습관, 제한 기능 때문에 왕복하는 경험 등 여러 후보가 있다. 구현 안전성과 지각된 신뢰를 같은 항목으로 묶으면 이미 해결된 엔진 안전을 다시 만들거나, 반대로 발견 가능성 문제를 놓친다.

**반증 가능 조건:** 실패/복구 사례 관찰, 오류율, 취소 후 결과, undo 성공률 또는 사용자가 작업을 실행하지 못한 이유를 수집해 “안전 결함”과 “안전 상태를 믿지 못함”을 분리해야 한다.

### 5. “이 다섯 가지가 핵심이다” — 가장 큰 약점은 사용자 빈도 자료 부재

**관찰 O13 (빈도 자료 없음):** README, `docs/behavior.md`, `CONTEXT.md`, 코드·테스트와 브리프를 `telemetry|analytics|usage|frequency|daily|workflow|user study|interview|survey|event log|metric|로그|빈도|사용자 조사|인터뷰|설문|일상`으로 검색했지만 사용자 행동 빈도, Finder 전환 횟수, 작업별 성공률, 시간 비용을 기록한 자료를 찾지 못했다. `Tests/IHateFinderTests/PaneDailyTests.swift`의 “Daily”는 테스트 클래스명이며 사용자 관찰 자료가 아니다.

**관찰 O14 (브리프도 가설 단계):** `doc/ulw-research/20261010-000001/brief.md:11-17`은 ideal end state를 “왜 Finder를 다시 켜는지 납득”하는 것으로 두고, `brief.md:21-30`은 검색·통합·연속성 등을 조사 축으로 정의한다. 축 정의는 결과 증거가 아니다. `brief.md:62-64`도 “검색 우선인가, 즐겨찾기/탭 우선인가”를 토론 대상으로 남긴다.

**반박:** 기능 목록과 경쟁 제품 표면만으로 “핵심”을 정하면 availability bias가 생긴다. 측정되지 않은 작업 빈도를 암묵적으로 가정한 상태다. 우선순위는 최소한 `발생 빈도 × Finder로 이탈할 확률 × 이탈 비용 × 구현 후 커버율`로 비교해야 한다. 현재 증거는 각 항목의 빈도와 이탈 확률을 채우지 못한다.

## 이미 구현된 것을 ‘없다’고 말할 위험 목록

1. **검색 전체가 없음:** 틀림. 현재 폴더 이름 거르기는 구현됨. 정확한 부재는 하위 폴더/Spotlight형 검색 (`docs/behavior.md:48-52`; `FilePaneController.swift:287-337`).
2. **장소 전환이 없음:** 틀림. 고정 위치·디스크 사이드바, 뒤/앞/위, 주소창이 있음 (`docs/behavior.md:8-18`; `BrowserWindowController.swift:528-632,848-878`).
3. **작업 맥락 복원이 없음:** 틀림. 양쪽 마지막 경로, 정렬, 숨김, 양쪽 창 표시를 저장함 (`README.md:158-168`; `WorkspaceStore.swift:3-93`). 정확한 부재는 탭과 사용자 정의 장소 저장.
4. **Finder 연동이 없음:** 틀림. 시스템 클립보드, 외부 drag, open-documents, Show in Finder, 기본 파일 뷰어 절차가 있음 (`README.md:72-79,171-227`; `AppDelegate.swift:8-37`).
5. **Quick Look이 없음:** 틀림. Space/Cmd-Y와 포커스 창 추적이 있음 (`docs/behavior.md:43-46`; `FilePaneController.swift:339-382`).
6. **실행 취소가 없음:** 틀림. 최근 50개 파일 작업 undo가 있고 redo만 없음 (`docs/behavior.md:116-121`; `README.md:106-117`).
7. **외부 변경 반영이 없음:** 틀림. 현재 폴더 외부 변경을 감지하고 URL 기준 선택을 유지한다고 명시·구현함 (`docs/behavior.md:30-34`; `BrowserSession.swift:150-191`). 런타임의 모든 파일시스템 조합이 성공한다고까지 확대해서는 안 됨.
8. **진행/취소/복구 피드백이 없음:** 틀림. 전송 상태, 취소, 부분 결과와 복구 위치가 정의돼 있음 (`docs/behavior.md:92-106`; `README.md:140-156`). 체감상 충분한지는 별도 사용자 관찰 문제.
9. **즐겨찾기가 없음:** 용어 주의. 사용자 정의 즐겨찾기는 없음이 맞지만 고정 “위치” 사이드바는 있음. 둘을 합쳐 “장소 기능 없음”이라 하면 오진.
10. **통합 때문에 Finder가 뜬다:** 인과 미확인. README가 밝힌 시스템 경계 때문에 Finder가 남는 경우와 지원 경로의 실패를 분리해야 함 (`README.md:220-227`).

## 비교 편향 목록

1. **기능 체크리스트 편향:** Finder/대안 제품의 기능 수를 기준으로 두면 IHateFinder의 의도적 중심(주소창·상세 목록·cut/paste·양쪽 창)을 무시한다 (`README.md:5`; `CONTEXT.md:1-3`).
2. **벤치마크 선택 편향:** Finder는 macOS 시스템 셸, 대안 관리자는 power-user 제품이다. 두 집단에서 공통으로 보이는 기능이 이 사용자의 핵심이라는 결론은 나오지 않는다.
3. **생존자/마케팅 편향:** 경쟁 제품 문서에 크게 노출된 기능은 차별화·판매 포인트일 수 있으며 실제 사용 빈도 자료가 아니다.
4. **플랫폼 권한 비대칭:** Finder의 Desktop/Open/Save/Dock 역할처럼 서드파티 앱이 동일하게 소유할 수 없는 표면을 제품 완성도 점수에 그대로 넣으면 구조적 불이익을 기능 결핍으로 오인한다 (`README.md:220-227`).
5. **명칭 등가 편향:** Finder “Search”와 현재 폴더 필터, Finder Favorites와 고정 Places, 시스템 통합과 open/reveal 지원은 이름이 비슷해도 범위가 다르다.
6. **최대 기능 사용자 편향:** 재귀 검색·탭·사용자 장소를 자주 쓰는 power user의 작업을 전체 일상 사용으로 일반화할 위험이 있다.
7. **신규성 편향:** 최근 추가된 undo/Quick Look/filter/open handling을 과거 상태의 인상으로 평가할 위험이 크다. git 기록상 `22f79b5`가 undo·Quick Look·filter·menu를 대규모로 추가했고 `7670195`가 안전성과 desktop integration을 추가했다.
8. **문서=실행 편향:** 반대 방향 위험도 있다. `docs/behavior.md`는 기준 문서이므로 코드 anchor로 교차 확인해야 한다. 본 보고서는 필터, 사이드바, 복원, open/reveal 소비 경로를 코드에서 확인했지만 실제 앱 QA는 수행하지 않았다.
9. **Finder 재등장=실패 편향:** 시스템 한계로 Finder가 뜬 것, 습관적으로 Finder를 연 것, 기능 미지원으로 전환한 것을 구분하지 않으면 통합 결핍을 과대평가한다.
10. **비용 무시 편향:** 빈도만 높아도 구현 비용과 해결 커버율이 낮을 수 있다. 반대로 낮은 빈도라도 데이터 손실 위험이 크면 안전 기능이 우선될 수 있다. 현재 엔진 안전장치의 존재 때문에 “신뢰” 추가 투자는 구체 결함이 있을 때만 정당화된다.

- **CLAIM-S2 (강함):** 장소 전환은 고정 위치·디스크·주소창·방문 이력·마지막 폴더 복원까지 구현됐지만, 사용자 정의 즐겨찾기는 저장 모델과 사이드바 생성 경로에 없다. 근거: `docs/behavior.md:8-18`, `BrowserWindowController.swift:848-878`, `WorkspaceStore.swift:3-48`.
- **CLAIM-S3 (강함):** 통합은 전무하지 않으며 clipboard/drag/open/reveal/default-viewer 경로가 있다. Finder가 남는 네 표면도 명시돼 있다. 근거: `README.md:72-79,171-227`, `AppDelegate.swift:8-37`, `BrowserWindowController.swift:199-218`.
- **CLAIM-S4 (강함):** 파일 작업 신뢰성의 기반 안전장치와 피드백은 이미 제품의 두꺼운 부분이다. “신뢰감 부족”은 런타임 오류나 사용자 관찰 없이 핵심 결핍으로 단정할 수 없다. 근거: `README.md:95-117,140-156`, `docs/behavior.md:70-121`.
- **CLAIM-S5 (강함):** 검색·즐겨찾기·통합·신뢰를 우선해야 한다는 빈도 기반 증거는 현재 자료에 없다. 기능 비교는 후보 생성에는 유효하지만 순위 결정 근거로는 부족하다.
- **CLAIM-S6 (중간):** 다음 구현을 고르기 전 최소한 Finder 전환 사건을 작업 단위로 기록해야 한다. 이는 코드 결론이 아니라 O13에서 도출한 연구 권고다.

## 권고하는 공격적 우선순위 게이트

1. 먼저 1~2주 또는 충분한 작업 표본 동안 `시작 작업 / IHateFinder에서 막힌 단계 / Finder로 전환한 이유 / 대체 경로 / 소요 시간 / 빈도`를 기록한다.
2. “검색”은 `현재 폴더 필터`, `알려진 경로 이동`, `위치 미상 전역 찾기`, `내용/메타데이터 검색`으로 분해한다.
3. “통합”은 `clipboard`, `drag`, `open-documents`, `Show in Finder`, `Open/Save`, `Desktop/Dock`, `Finder 직접 호출 앱`으로 분해한다.
4. “신뢰”는 `실제 작업 실패`, `복구 실패`, `상태 미표시`, `생소해서 불안`, `시스템상 Finder 재등장`으로 분해한다.
5. 사용자 정의 즐겨찾기는 “반복 이동이 실제 상위 이탈 원인”일 때만 우선한다. 그 전에는 명확한 부재이지만 핵심 결핍으로 승격하지 않는다.
6. 경쟁 제품 기능은 이 로그에서 드러난 작업을 해결하는 패턴을 찾는 데만 사용하고, 제품별 기능 개수를 순위 근거로 쓰지 않는다.

## 반대 증거와 한계

- 사용자 본인의 “0.3 Finder” 평가는 강한 정성 신호다. 다만 어느 작업에서 왜 그렇게 느꼈는지는 현재 자료에 없다.
- 하위 폴더 검색, 사용자 정의 즐겨찾기, 탭/아이콘/열 보기가 명시적으로 없으므로 실제로 자주 쓰는 사용자에게는 큰 결핍일 수 있다 (`README.md:229-236`). 본 보고서는 부재를 부정하지 않고 우선순위 인과만 공격한다.
- 문서와 코드 교차 확인은 했지만 제품 테스트·빌드·실사용 QA는 과업 지시에 따라 하지 않았다. 따라서 “코드 경로가 존재한다”와 “모든 실제 환경에서 신뢰성 있게 작동한다”를 구분한다.
- 사용성·발견 가능성은 정적 코드만으로 판단할 수 없다. 구현돼 있어도 사용자가 찾지 못하면 체감상 없는 기능이 될 수 있다.

- **LEAD — 검색 의도 분포:** 이름·내용·메타데이터·위치 미상·현재 폴더 좁히기의 비율을 수집하라. “검색” 단일 기능으로 묶으면 잘못된 구현을 고를 수 있다.
- **LEAD — 반복 목적지 집합:** 최근 작업에서 고정 Places 밖의 목적지가 몇 개이고 얼마나 반복되는지 측정하라. 사용자 즐겨찾기의 기대 커버율을 계산할 수 있다.
- **LEAD — 통합 실패 대 시스템 경계:** Finder 재등장마다 README의 네 한계 범주인지, 지원된 open/reveal/clipboard/drag 경로의 실패인지 태깅하라.
